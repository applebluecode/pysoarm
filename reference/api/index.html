    API reference¶

    Complete reference for the public API of pysoarm 0.1.1. Every symbol documented here is importable from the top-level package:

    from pysoarm import SOArm, ArmState, Calibration, SafetyLimits, Pose

    The reference sections are generated from the docstrings by mkdocstrings, so this page and the code cannot drift apart. Start with Conventions and Public API at a glance; task-oriented examples live in the Quickstart.

    Conventions¶

    The rules below hold across the whole API. Read them once — the rest of the reference assumes them.

    Units¶

    Quantity Unit Where
    Joint positions, goals, limits, step guard degrees SOArm, ArmState.q_deg, Calibration, SafetyLimits
    Joint positions, ROS bridge input radians only ArmBridge.command_from_radians
    Cartesian position metres Pose.x/y/z
    Orientation unit quaternion (w, x, y, z) Pose.qw/qx/qy/qz
    Euler angles, Pose.angle_to degrees (radians for angle_to) Pose.from_xyz_rpy, Pose.to_xyz_rpy
    Time, timestamps, durations seconds ArmState.t, duration=, hz= in Hz
    Temperature, voltage °C, V ArmState.temperature_c, ArmState.voltage_v

    Raw servo quantities are not SI and are never silently converted: ArmState.speed_raw and ArmState.current are present_speed / present_current register counts. Use Register.to_unit() when a physical unit matters.

    Joint order¶

    Every joint tuple and every sequence argument uses the model's joint order, which is the same for SO-100 and SO-101:

    Index 0 1 2 3 4 5
    Joint shoulder_pan shoulder_lift elbow_flex wrist_flex wrist_roll gripper
    Motor id 1 2 3 4 5 6

    Pass a different RobotModel to change order, ids or count. Sequences that are too short, too long, non-finite, or not in this order raise ConfigurationError before anything is sent to the bus.

    Values are immutable¶

    ArmState, Pose, SafetyReport, JointStateFrame, LoopStats, Register, JointCalibration and RobotModel are frozen dataclasses (JointStateFrame, LoopStats and SafetyReport are plain frozen containers): they are snapshots, never mutated in place. The only stateful objects are SOArm, ArmBridge, the bus transports and Calibration.

    Nothing is clipped silently¶

    SOArm.write_goal() and ArmBridge.command() return the goal that was actually written. Guards clip or derate, and the difference is visible in SafetyReport and in the returned tuple. SOArm.move_to() returns the state measured after the move.

    Lifetime and threading¶

    SOArm owns its bus: construct it, connect() (or use with), use it, stop(). stop() is idempotent and never raises, so it is safe in a finally block.

    from pysoarm import SOArm

with SOArm(port="/dev/so101_follower", calibration="follower.json") as arm:
    arm.hold()
# leaving the block disables torque and closes the port

    Instances are not thread-safe: one owner thread per arm. The serial port is exclusive (BusConnectionError if another process holds it). Callbacks passed to SOArm.run_control_loop() run on the loop thread and must not block.

    Clock and injection seams¶

    Construction takes clock= (defaults to time.monotonic), sleep= and — where a dependency is optional — an explicit module seam (placo_module, rustypot_module, serial_factory). Tests use these to run the real code paths with FakeBus and no hardware.

    Device layer: pysoarm.arm¶

    The lifecycle¶

    construct ──► connect() ──► read_once()/write_goal()/move_to() ──► stop()
              │             └── run_control_loop() (owns the loop)
              └── open bus → configure motors (torque off) → hold measured pose → torque on

    connect() is deliberately conservative: torque stays off while the motors are configured, the measured pose is written back as the first goal, and only then is torque enabled — the arm cannot jump on connect. The steps are idempotent where possible; calling connect() twice is harmless, and stop() may be called at any time in any state.

    Typical calls¶

    from pysoarm import SOArm

arm = SOArm(port="/dev/so101_follower", calibration="follower.json")
arm.connect()

state = arm.read_once()          # q_deg, temperature_c, voltage_v, t, ...
arm.hold()                       # re-read and command the measured pose

goal = arm.write_goal([0, -30, 60, 0, 90, 40])   # returns what was written
arm.move_to([0, -20, 60, 0, 90, 40], duration=2.0, profile="minjerk")

def policy(state, elapsed_s):
    return state.q_deg           # None means "hold, send nothing"

stats = arm.run_control_loop(policy, hz=200, duration=5.0)
print(stats.ticks, stats.overruns)
arm.stop()

    Reading states¶

    health= Registers refreshed Transactions per tick
    False none (cache reused) 1 sync read — the hot path
    True all health registers 1 sync read + 1 read
    None (default) one health register per tick, round-robin, once the cache is older than health_period_s 1 sync read (+1 periodically)

    That amortisation is what keeps a 200 Hz loop inside its 5 ms budget while temperature and voltage stay fresh enough for the guards.

    pysoarm.arm ¶

    SOArm — the high-level device object.

    Shaped after pylibfranka.Robot / pyAgxArm so calling code reads the same way, within what position-servo hardware allows::

    with SOArm(port="/dev/so101_follower", calibration="follower.json") as arm:
    state = arm.read_once()
    arm.move_to([0, -30, 60, 0, 90, 40], duration=2.0)
    arm.run_control_loop(lambda s, t: policy(s), hz=200, duration=5.0)

    Design rules:

    • hold before you move — connect() reads the measured pose and writes it back as the first goal, so the first command can never be a jump;
    • clipping is observable — write_goal() returns the goal actually sent, never silently reduced;
    • one sync read + one sync write per control tick — health registers are cached and refreshed every health_period_s instead of on every tick;
    • stop() is idempotent and safe from finally/signal handlers — it disables torque then closes the bus, in that order.

    connect ¶

    connect(*, allow_model_mismatch=False)

    Open the bus, configure the motors, hold the current pose, enable torque.

    The sequence is deliberately conservative: torque is off while the motors are configured, the measured pose is written back as the first goal, and only then is torque enabled. A leader is never commanded and its torque is never enabled.

    allow_model_mismatch bool

    		 False

    Raises:

    Type Description

    Port unavailable or a motor did not answer.
    ConfigurationError

    The servos report an unexpected model number.
    CalibrationError

    Calibration missing, incomplete or mismatched.
    CommunicationError

    A register transaction failed after retries.

    stop ¶

    stop()

    Disable torque (best effort) and close the bus. Idempotent; never raises.

    read_once ¶

    read_once(
    health=None, *, retries=None, health_period_s=None
)

    Read the arm once.

    Parameters:

    Name Type Description Default
    health bool | None

    True refreshes all health registers at once, False reuses the cache, None (default) refreshes one register per tick (round-robin) once the cache is older than health_period_s.     Calibration: pysoarm.calibration¶

    Calibration maps raw ticks to degrees and defines each joint's usable travel. It comes from one of three places:

    1. a Calibration object you build,
    2. a LeRobot JSON file (.from_lerobot(path) / to_lerobot(path) — pysoarm reads LeRobot's format directly, so a calibrated arm does not need calibrating again),
    3. the motors themselves (calibration=None at construction reads the stored calibration).

    validate(model) is called by connect(): missing joints, extra joints or duplicated motor ids raise CalibrationError before any motor is commanded.

    The motor-side flow is public in pysoarm.calibration:

    Function Purpose
    read_calibration(bus, model) read limits + homing offsets from the servos
    write_calibration(bus, model, cal) persist a calibration to the servos
    reset_calibration(bus, model) clear offsets, widen travel to 0..4095
    set_half_turn_homings(bus, model) Feetech offset = position - 2047
    record_ranges(bus, model, stop=...) poll travel while the operator moves the arm
    calibrate(bus, model, role=..., full_turn=...) the full flow above

    Safety: pysoarm.safety¶

    Every goal passes the same guard chain in write_goal() — there is no bypass flag:

    Order Guard Threshold On trip
    1 Finiteness — SafetyViolation
    2 Watchdog max_consecutive_failures WatchdogTimeout (torque already off)
    3 Temperature temp_max_c SafetyViolation
    4 Voltage voltage_min_v SafetyViolation
    5 Calibrated limits limit_margin_deg goal clamped inward, clipped=True
    6 Step size max_step_deg (scaled by the derate factor) goal clipped to state.q_deg ± max_step
    7 Derating temp_warn_c SafetyLimits.derate() returns a factor in (0.25, 1.0] from the hottest motor, which shrinks the allowed step

    SafetyLimits() defaults are the reference values used on the reference arm:

    Field Default Meaning
    max_step_deg 5.0 Largest change of a joint between two goals
    limit_margin_deg 1.0 Margin kept inside the calibrated travel
    temp_warn_c 55.0 Above this, goals are derated
    temp_max_c 70.0 At this, goals are refused
    voltage_min_v 10.0 Below this, goals are refused
    max_consecutive_failures 3 Read failures before the watchdog trips

    The contract on tripping is part of the API: WatchdogTimeout leaves torque off, and SafetyViolation/CalibrationError/NotReachableError are raised before a goal is written, so the arm keeps its last safe target. Temperature is judged on the hottest motor (ArmState.max_temperature_c) and voltage on the lowest one (ArmState.min_voltage_v).

    pysoarm.safety ¶

    Safety guards applied to every goal before it reaches the bus.

    Guards are pure functions of the requested goal, the current state and the limits, so all the rules are unit-testable without hardware. They run in this order:

    1. validity — correct joint count, finite values, known joints (ConfigurationError);
    2. watchdog — too many consecutive read failures (WatchdogTimeout);
    3. thermal / supply — too hot or undervoltage (SafetyViolation);
    4. soft limits — clamp to the calibrated travel minus a margin;
    5. per-step clipping — |q_goal - q_now| <= max_step_deg * derate, the guard that makes the first goal after connect (and every goal after a lost frame) unable to cause a jump.

    pysoarm.bus.base ¶

    The Bus protocol: the only boundary the control code is allowed to cross.

    Above this boundary nothing imports serial or rustypot and everything is expressed in raw register values; below it nothing knows about degrees, calibration or limits. That split is what lets the whole control path run against :class:~pysoarm.bus.fake.FakeBus in tests.

    Implementations must honour these rules:

    • one batch call per control step — call sync_read/sync_write instead of looping in application code. On this hardware sync_read is internally sequential (the TTL bus is half-duplex), but keeping it a single call is what makes swapping in a faster backend or a fake painless;
    • retries are idempotent — a retry must not change the value written;
    • raise, do not block — a missing reply becomes :class:~pysoarm.exceptions.CommunicationError after the configured retries, with the raw bytes attached for post-mortem;
    • stateless — no calibration, no unit conversion, no clipping. Those live above.

    pysoarm.bus.scs ¶

    SCS protocol over pyserial — the reference backend and the only hard dependency.

    Wire format (Feetech SCS/STS, 8N1, 1 Mbaud)::

    request   FF FF  ID  LEN  INSTR  [PARAMS...]  CHECKSUM
response  FF FF  ID  LEN  ERROR  [DATA...]    CHECKSUM

    with LEN = len(PARAMS) + 2 (a two-byte READ therefore uses LEN = 4 — the value most easily got wrong), CHECKSUM = ~(ID + LEN + INSTR + PARAMS) & 0xFF and broadcast id 0xFE. Instructions used here: PING 0x01, READ 0x02, WRITE 0x03, SYNC_WRITE 0x83.

    The bus is half-duplex: while the host transmits, a servo's reply cannot be on the wire. Pipelining requests (sending all six before reading any reply) therefore corrupts the stream on real hardware — measured, and the reason :meth:ScsBus.sync_read issues one request/response pair per servo and collects them into one mapping. Broadcast SYNC_WRITE is the exception: the host is the only transmitter, so six goals go out in a single frame.

    Measured on the reference hardware (six joints, 1 Mbaud, this backend): single register read 0.30 ms, six-joint sync_read ~1.8 ms (sequential pairs), six-goal sync_write 0.26 ms. A Rust driver (rustypot) pipelines at a lower level and reaches ~1 ms; this module trades that for zero non-Python dependencies.

    pysoarm.bus.rustypot ¶

    Optional rustypot backend: the same bus, driven from Rust.

    rustypot is the driver LeRobot uses for the STS3215. It speaks the same SCS protocol but does the request/response bookkeeping in Rust, so a six-joint read costs ~1 ms instead of the ~2.2 ms the pure-Python :class:~pysoarm.bus.scs.ScsBus needs. It is an optional extra::

    pip install "pysoarm[rustypot]"

    Select it explicitly — SOArm(..., backend="rustypot"), pysoarm scan --backend rustypot — or pass backend="auto" to use it when it is importable and fall back to scs otherwise.

    Notes on the mapping:

    • rustypot does not reject writes to read-only registers, so this adapter checks :data:~pysoarm.bus.registers.REGISTERS first (same behaviour as ScsBus);
    • rustypot raises ValueError for a bad id/register name, RuntimeError for a bus failure and OSError when the port cannot be opened; these are translated to :class:~pysoarm.exceptions.ConfigurationError, CommunicationError and BusConnectionError respectively;
    • the port is opened with an exclusive lock, so a second process fails loudly.

    SO-101 / SO-100 description.

    Six STS3215 servos, ids 1-6, in this order (the order every array in this package uses)::

    Kinematics: pysoarm.kinematics¶

    Kinematics is optional and out of the control loop: the position loop works in joint space, and kinematics only converts to and from Cartesian goals. A SO-101 URDF is not shipped (licensing and the accuracy of community meshes vary) — pass your own.

    from pysoarm import SOArm
from pysoarm.kinematics import PlacoKinematics

arm = SOArm(
    port="/dev/so101_follower",
    calibration="follower.json",
    kinematics=PlacoKinematics("so101.urdf", target_frame="gripper_frame_link"),
)
with arm:
    pose = arm.forward()                     # FK of the current joints
    arm.move_to_pose(pose, duration=2.0)     # IK, then a joint-space move

    import pysoarm stays dependency-free: the placo adapter is imported lazily on first use, and a missing dependency raises KinematicsError with the install command. move_to_pose() solves IK before writing any goal, so an unreachable target raises NotReachableError and leaves the arm where it was.

    pysoarm.kinematics.placo_solver ¶

    Inverse/forward kinematics through placo (optional extra).

    placo builds a kinematic model from a URDF and solves frame tasks with a damped least-squares step. The adapters here:

    • work in degrees and metres at the boundary (radians internally, as placo expects);
    • use a small task gain (1e-3) and iterate until the position residual is below tolerance_m — a gain of 1.0 overshoots and lands in a wrong branch on the reference two-link model, so the default is deliberately conservative;
    • seed the solver from the current joint configuration (a Cartesian move from the current pose converges in a handful of iterations);
    • raise :class:~pysoarm.exceptions.NotReachableError with the residual instead of returning a saturated joint vector.

    Orientation is not constrained by default (orientation_gain=0): a 4-DoF arm cannot meet a full 6-D pose, and silently trading position against orientation is worse than ignoring it. Set orientation_gain on arms with enough degrees of freedom.

    Exceptions: pysoarm.exceptions¶

    Every error derives from PysoarmError, so one except can catch this package without swallowing unrelated OSError/ValueError:

    PysoarmError
├── ConfigurationError        bad arguments, unknown joint/register, bad calibration
├── BusConnectionError        port unavailable or held by another process
├── CommunicationError        no reply / corrupt packet; arm holds its last goal
│                             (.motor_id, .register, .raw)
├── CalibrationError          calibration missing, incomplete or mismatched
├── SafetyViolation           non-finite goal, over-temperature, undervoltage
│   └── WatchdogTimeout       too many consecutive read failures; torque is off
└── KinematicsError           kinematics unavailable or failed
    └── NotReachableError     IK did not converge; no goal was written

    The recovery contract is part of the type: WatchdogTimeout means torque is already off, and the errors raised during a move mean no goal was written, so a try/except around a move leaves the arm in a defined state.

    pysoarm.exceptions ¶

    Exception hierarchy.

    Every error raised by this package derives from :class:PysoarmError, so callers can catch one type without swallowing unrelated failures (OSError from pyserial, ValueError from user code, ...).

    Physical safety is treated as part of the contract: :class:WatchdogTimeout and :class:SafetyViolation must leave the arm in a defined state (torque off or last safe goal), and that is stated in their docstrings.
